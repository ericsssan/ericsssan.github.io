From Production Flamegraph to Fixed Megamorphic Call Site

Profilers tell you where time goes. They don't tell you why the JIT gave up.

Eric San 2026 Source on GitHub →

There's a class of production performance problem that profilers can locate but not explain. The flamegraph is unambiguous — handleEvent is eating 40% of CPU. The function looks fine. Local benchmarks look fine. The problem isn't in the code; it's in what the runtime decided to do with it.

V8 optimizes by speculating on object shapes. When too many distinct shapes flow through a property access, V8 gives up on the fast path — megamorphism — and falls back to a hashtable lookup on every access. This doesn't show up in source. It's a runtime fact, invisible to the reader and undetectable by profiler sampling.

This article shows the full loop: find it with --log-ic, fix it at the shape boundary, enforce it in CI.

Benchmark — 2,000,000 events, 20 hot iterations
broken   229.4ms   (megamorphic loads, un-inlinable call)
fixed     54.5ms   (monomorphic loads, inlined)   ← ~4.2× faster

The fix is one line at the ingestion boundary. broken/handler.js and fixed/handler.js are byte-for-byte identical.

How V8 executes your code

V8 runs JavaScript in three tiers:

Ignition (interpreter) → Maglev (mid-tier JIT) → Turbofan (optimizing compiler)

At each property access (.type, .id, etc.), Ignition maintains an inline cache (IC) — a record of which object shapes (hidden classes) that site has seen:

  • monomorphic — 1 shape → direct memory load, very fast
  • polymorphic — 2–4 shapes → small dispatch table, still fast
  • megamorphic — 5+ shapes → generic hash-table lookup, permanently slow

When a function gets hot, Turbofan reads the IC feedback Ignition collected, then replaces the IC with specialized machine code. Megamorphic IC feedback causes Turbofan to emit permanently slower code — and that decision is baked in for the lifetime of the process.

This is why the bug is invisible in source: the slow path is a runtime decision made before your hot loop even starts.

Finding it with --log-ic

Node exposes V8's IC log via --log-ic. Run the broken path under tracing:

node --log-ic --prof broken/drive.js

The log records every IC state transition. You'll see handleEvent's property accesses cycling through monomorphic → polymorphic → megamorphic as different event shapes flow through. Once a site goes megamorphic, it stays there.

For a cleaner signal, use ic-fuzzer to find the minimal set of shapes that cause the problem:

node bin/ic-fuzzer.js ../broken/handler.js handleEvent \
  --seed='{"type":"click","id":1,"value":2}'
[ic-fuzzer] minimal set: 5 shape(s)  (0 shrink step(s))

   1. literal:type-id-value         { type, id, value }  literal
   2. incr:type-value-id            e.type; e.value; e.id  incremental
   3. incr:id-type-value            e.id; e.type; e.value  incremental
   4. incr:value-type-id            e.value; e.type; e.id  incremental
   5. incr:value-id-type            e.value; e.id; e.type  incremental

[ic-fuzzer] IC sites at megamorphic:
    [MEGAMORPHIC ]  .id     handleEvent  (broken/handler.js:10:16)
    [MEGAMORPHIC ]  .type   handleEvent  (broken/handler.js:10:32)
    [MEGAMORPHIC ]  .value  handleEvent  (broken/handler.js:10:52)

Five distinct shapes — that's the threshold. In production, events arrive from multiple producers with subtly different property insertion orders, which means five shapes is trivially reached.

The fix

Shape diversity usually enters at a system boundary — where events from external sources hit your hot path. The fix is to normalize there: coerce all incoming objects to a single canonical shape before the hot code sees them.

// fixed/event.js — the boundary normalizer
function toEvent(raw) {
  return { type: raw.type, id: raw.id, value: raw.value };
}

// drive.js — normalize at ingestion, not in the hot path
events.forEach(raw => handleEvent(toEvent(raw)));

Now every object that reaches handleEvent has the same hidden class. V8 sees one shape, stays monomorphic, Turbofan inlines the property accesses as direct memory loads. The hot path didn't change at all.

Enforcing it in CI

Shape normalization is easy to regress — someone adds a field to an event type upstream, and the canonical shape silently diverges. A CI gate catches this before it ships:

// ci/monomorphic-gate.js
const { probe, derive } = require('ic-fuzzer');

const file = path.resolve('src/handler.js');
const seed = { type: 'click', id: 1, value: 2 };

const five = derive(seed).slice(0, 5);   // five shapes → enough to trigger megamorphism
const { severity } = await probe(file, 'handleEvent', five);

if (severity >= 3) {
  console.error(`handleEvent is megamorphic — normalize at the boundary`);
  process.exit(1);
}

Drop-in GitHub Actions job in .github/workflows/deopt-gate.yml. The gate fails on broken/handler.js and passes on fixed/handler.js.

The full workflow

  1. Find it. Run ic-fuzzer to get the minimal shape set and the exact IC sites going megamorphic.
  2. Quantify it. Use --bench to get a timing ratio before touching the code. Know what you're fixing.
  3. Fix it. Write a boundary normalizer that coerces all inputs to a single canonical shape. The hot path stays untouched.
  4. Verify it. Run --assert-max=monomorphic on the hot path. Gate it in CI so it can't regress.

ic-fuzzer: how it works

ic-fuzzer uses IC severity — not crashes or coverage — as the feedback signal. It derives shape variants from a seed object (different property insertion orders, extra fields, class instances vs. literals), then uses a fast-check loop to find the minimal set that pushes a call site to megamorphic and shrinks it.

The key insight is that V8's IC transitions are deterministic given a fixed property access sequence. That makes them tractable to search over: you don't need random mutations, you need systematic shape variation.

SituationCauseWhat to do
No IC dataWrong export name, or seed doesn't trigger the call pathFix the seed
X/no_feedback stateTurbofan compiled before the probe ran; IC sites replacedUse --no-turbofan
No property accessesFunction doesn't read properties on its argumentic-fuzzer doesn't apply

Flags: --target=polymorphic, --corpus, --watch (redirect IC collection to a library file), --bench, --assert-max, --no-turbofan, --trace-deopt, --report-maps, --rng (reproduce a run).

The repo also ships a full programmatic API (probe, fuzz, bench, derive) for integrating into test suites or building custom harnesses around private functions.
